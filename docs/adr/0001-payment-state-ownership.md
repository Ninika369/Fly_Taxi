# ADR-0001: Assign Payment State Ownership to `service-order`

- **Status:** Accepted
- **Date:** 2026-07-26
- **Decision scope:** Existing FlyTaxi Java/Spring architecture
- **Implementation status:** Planned. This ADR records the target boundary; this pull request does not implement it.

## Context

FlyTaxi currently separates order handling from the Alipay SDK integration:

- `service-order` owns the order lifecycle, the order database connection, the calculated order price, and the current paid or unpaid order status.
- `service-pay` wraps the Alipay SDK and callback protocol, but currently has no datasource, MyBatis mapper, or independent payment-domain persistence in the repository.
- The current driver-side payment prompt accepts caller-supplied `orderId`, `price`, and `passengerId`.
- The current Alipay page endpoint accepts caller-supplied `subject`, `outTradeNo`, and `totalAmount`.
- The current callback path treats `out_trade_no` as a numeric `orderId` and asks `service-order` to mark that order paid.
- The repository does not yet contain a durable payment-intent or payment-transaction model.

These are current implementation facts, not the accepted target design. They leave the payable amount and identity insufficiently server-owned, couple a provider-facing trade number to the internal order ID, and provide no durable correlation or idempotency record for callback processing.

Adding an independent payment database to `service-pay` would also split order and payment-state transitions across services before the project has a reliable distributed consistency mechanism.

## Decision

### Authoritative ownership

`service-order` will own the authoritative payment-domain state for the current architecture.

Its responsibilities will include:

- deriving the payable amount from the persisted order;
- deriving the passenger and ownership relationship from the persisted order and authenticated principal;
- validating whether the order is in a legal state for payment;
- creating and persisting payment intents;
- persisting payment transactions or normalized provider-callback records;
- enforcing payment idempotency and legal state transitions;
- updating payment state and order state within the same local database transaction;
- exposing the internal commands required to create an intent and apply a verified provider result.

`service-pay` will remain a provider adapter.

Its responsibilities will include:

- holding external provider configuration;
- calling the Alipay SDK;
- translating internal payment commands into provider requests;
- verifying callback signatures and provider-identity fields;
- validating that required provider fields are present and parseable;
- normalizing provider responses and callbacks into an internal contract;
- returning provider-specific acknowledgement or retry responses.

`service-pay` will not own the authoritative order, amount, payment-intent, or payment-transaction state and will not receive an independent datasource in this phase.

### Ownership matrix

| Responsibility | `service-order` | `service-pay` |
|---|---:|---:|
| Persisted order and payable amount | Owner | No |
| Passenger ownership and legal order state | Owner | No |
| Payment intent and payment status | Owner | No |
| Provider transaction correlation record | Owner | No |
| Alipay SDK and provider configuration | No | Owner |
| Provider request construction | Supplies trusted values | Executes adapter logic |
| Callback signature and provider-identity verification | Consumes verified result | Owner |
| Amount, order, intent, and state comparison | Owner | No |
| Final order-paid transition | Owner | No |
| Provider acknowledgement text or protocol response | Supplies processing result | Owner |

### Payment identifiers and data semantics

- `out_trade_no` will be a provider-compatible, unique, opaque payment-intent identifier generated by `service-order`.
- `out_trade_no` will not equal the internal `orderId` and must never be parsed as a numeric order ID.
- A payment intent must be associated with one order and one authoritative payable amount.
- Amount and currency semantics must be explicit and immutable after intent creation. The implementation must either persist the currency or document and enforce a single-currency invariant.
- An order may retain historical terminal intents, but it must not have competing active payment intents.
- A provider transaction identifier such as `provider_trade_no` must be unique when present.
- A payment transaction or callback record must retain enough normalized information to audit the provider result, verification outcome, processing outcome, and timestamps without storing credentials or unnecessary sensitive payloads.
- Exact table names, columns, indexes, status values, and retention rules will be defined in reviewed migration and implementation pull requests. This ADR does not create a schema.

### Target command flow

1. An authenticated passenger requests payment through a protected passenger-edge endpoint using only the order ID.
2. `service-order` resolves the caller from the authenticated principal, loads the order, verifies ownership and legal state, and reads the authoritative amount.
3. In a short local transaction, `service-order` creates or idempotently reuses the appropriate payment intent.
4. After that transaction commits, `service-order` sends trusted intent data to `service-pay`. A database transaction must not remain open across the provider call.
5. `service-pay` builds the Alipay request from server-supplied intent data and returns the provider response required by the caller.
6. Alipay notifications enter through `service-pay`, which verifies the provider signature and provider-identity fields before producing a normalized internal callback command.
7. `service-order` loads the intent by `out_trade_no`, compares the provider amount and transaction identifiers with persisted facts, validates the legal predecessor states, and records the callback result.
8. In one local conditional transaction, `service-order` updates the payment intent, payment transaction record, and order-paid state.
9. A repeated valid callback returns an idempotent success without repeating the state transition or notification.
10. A signature failure, identity mismatch, amount mismatch, unknown intent, duplicate provider transaction conflict, or illegal state must not mark the order paid.
11. `service-pay` returns the provider success acknowledgement only when `service-order` reports that the callback was newly applied or had already been applied idempotently. Otherwise it returns the provider-defined failure or retry response.
12. Any SSE notification or later outbox delivery occurs after the authoritative database commit and is not part of the payment correctness transaction.

### Required invariants

- Clients do not choose the authoritative amount, passenger ID, or `out_trade_no`.
- `orderId` and `out_trade_no` are separate identifiers with separate purposes.
- `service-pay` cannot independently mark an order paid.
- An order is marked paid only after a verified and domain-valid provider result.
- Payment and order-state changes use conditional updates and affected-row checks.
- Duplicate callbacks cannot repeat payment transitions or downstream notifications.
- Provider transaction identifiers cannot be silently associated with multiple intents.
- Remote provider or Feign calls do not run inside the local database transaction.
- Logs and persisted callback records do not contain provider private keys, access credentials, or unnecessary sensitive payloads.

## Consequences

### Positive

- The database that already owns the order can update payment and order state atomically.
- The payable amount and passenger relationship become server-owned.
- Callback processing gains durable correlation, auditing, and idempotency.
- `service-pay` stays focused on provider-specific SDK and protocol concerns.
- The design avoids introducing a distributed transaction between order and payment databases.
- A later outbox, retry worker, or message queue can build on the same state model.

### Costs and trade-offs

- `service-order` gains additional payment-domain tables and transition logic.
- New internal contracts are required between `service-order` and `service-pay`.
- Existing caller-controlled payment endpoints must be deprecated or replaced.
- Callback handling requires migration, concurrency, replay, mismatch, and idempotency tests.
- Provider availability remains a remote dependency even though authoritative state changes remain local.

## Alternatives considered

### Let `service-pay` own an independent payment database

Rejected for the current phase. It would split the order-paid transition and payment result across databases before FlyTaxi has outbox-based coordination, reliable event delivery, or a demonstrated need for an independently scaled payment domain.

### Keep `orderId` as `out_trade_no`

Rejected. It couples an internal aggregate identifier to a provider-facing payment attempt, prevents clean retry or multi-provider semantics, and encourages callback code to bypass payment-intent validation.

### Continue accepting amount and passenger identity from the client

Rejected. These values must be derived from authenticated and persisted server-side facts.

### Persist duplicate authoritative payment state in both services

Rejected. Dual ownership would create disagreement and recovery ambiguity.

### Hold a database transaction open while calling Alipay

Rejected. Remote latency and failure must not extend the local transaction or lock duration.

## Implementation sequence

This decision must be implemented through separate reviewable pull requests:

1. Create database preflight, migration, rollback, and verification artifacts using the repository’s `database/` workflow.
2. Add the payment-intent and payment-transaction domain model to `service-order`.
3. Add uniqueness, conditional-update, and idempotency tests.
4. Add the protected passenger payment-intent endpoint with server-derived ownership and amount.
5. Add the trusted internal provider-request contract from `service-order` to `service-pay`.
6. Replace numeric `out_trade_no` parsing with payment-intent lookup.
7. Add normalized, verified callback handling and transactional order/payment updates.
8. Add replay, signature-failure, amount-mismatch, unknown-intent, provider-transaction-conflict, and duplicate-callback tests.
9. Move notification delivery after commit and make it idempotent or outbox-backed.
10. Deprecate the current caller-controlled payment entry points and update public documentation.

The separate principal and security-support ADR must be completed before treating the passenger endpoint or service-to-service calls as authenticated.

## Non-goals

This ADR does not:

- implement payment tables, DTOs, services, endpoints, migrations, or tests;
- add a datasource to `service-pay`;
- define refunds, chargebacks, settlements, reconciliation, or accounting-ledger behaviour;
- choose a message queue, service mesh, or external payment-orchestration platform;
- define user-session, principal, or service-token architecture;
- claim that the existing payment path is already safe or complete.

## Future reassessment

A future ADR may move the payment domain to an independent service and database if multiple providers, refunds, chargebacks, reconciliation, settlement, compliance, or independent scaling make that boundary worthwhile.

Such a split must include an explicit migration and consistency design. It must not occur by silently adding a second authoritative payment store.
